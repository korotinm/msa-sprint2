### Переключение на микросервис Booking

Стратегия миграции предполагает перенос данных бронирования из монолита в сервис без отключения функционала 

Перенос данных booking из монолита:
- доработка монолита - на запись в обе таблицы бронирования
- логика монолита перезаписывает по порядку ID записи в БД микросервиса идемпотентно `on conflict do nothing`
- как только все перелили в монолите отключается запись в его таблицу бронирования
- "мусор" для переливки выпилим до следующего релиза


### Поток данных для аналитического отдела

После переключения на monolith --gRPC--> booking - сервис booking асинхронно пишет события бронирования в Kafka

Сервис booking-history-service вычитывает сообщения и сохраняет в свою БД - аналитики получают данные с минимальными задержками(миллисекунды).

#### БД для исторических данных

Сервис booking-history-service масштабируется горизонтально. Его БД можно развернуть в конфигурации master(write) -> slave(read only),
таким образом разгрузив master-ноду предоставив ее только для записи - позволит ускорить запись.

Еще можно для таблицы исторических данных убрать все индексы кроме первичного ключа, что тоже ускорит запись в таблицу.

Дальше уже используя ноду read only формировать различные материализованные представления с любой вариативностью для аналитического отдела.
