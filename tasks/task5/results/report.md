- скопировал урок 4 -> 5
- для возможности развертывания одного сервиса но с разными версиями было создано два values файла для каждой версии
- в каждый файл был добавлен флаг create - в одном ture, другом false - чтобы один раз service создался
- в файле темплейт deployment бил модифицирован lable.app и выполнен проброс версии из values
- сюда же добавил энв SERVICE-VERSION для скрипта чтобы при его вызове можно было вывести версию для доказательства, что балансировака работает
- в servive.yaml добавлено условие что если флаг create=true то блок фала применяется, то есть это будет выполнено один раз
- поставил istio (istioctl install --set profile=demo), включил автоинъекцию сайдкаров в default namespace - поды стали 2/2, второй контейнер это прокси envoy
- сделал gateway.yaml - это точка входа в mesh, слушает 80 порт на istio-ingressgateway - потребовался для работы балансировщика, без него через порт-форвард трафик идет к одному поду
- поэтому форвардить буду так:  kubectl port-forward svc/istio-ingressgateway -n istio-system 9090:80
- сделал destination-rule.yaml - там subsets v1/v2 по лейблу version, плюс connectionPool и outlierDetection (это и есть circuit breaker - выкидывает под из балансировки после ошибок)
- сделал virtual-service.yaml - там два правила по порядку: первое ловит заголовок X-Feature-Enabled=true и шлет на v2, второе делит трафик 90/10 между v1 и v2
- проверил канареечное распределение - на 20 запросах вышло 19 v1 и 1 v2, что укладывается в 90/10
- проверил фича флаг - с заголовком всегда приходит v2
- Retry настроил в virtual-service, а не в destination-rule как сказано в задании, потому что в istio ретраи задаются только на уровне VirtualService, в DestinationRule такого поля нет. В DestinationRule остался circuit breaking
- по fallback история такая: Погасил v1 и увидел 503 no healthy upstream. Оказалось что автоматом трафик на живой под не переедет: веса 90/10 это два разных кластера envoy, а outlierDetection работает только внутри одного кластера. Ретрай тоже не помогает - он повторяет в тот же кластер и subset не меняет
- поэтому fallback сделал через отдельный манифест virtual-service-fallback-v1.yaml с весами v1=0 v2=100. При отказе v1 применяем его и весь трафик идет на v2. То есть это переключение оператором или автоматизацией, а не само
- правильный автоматический вариант это aggregate cluster в envoy с приоритетами (v1 priority 0, v2 priority 1), тогда envoy сам переключается когда в первом нет живых хостов. Не стал делать из-за сложности конфига, но механику посмотрел
- сделал envoy-filter.yaml с lua фильтром на ingressgateway, он при заголовке X-Feature-Enabled=true проставляет метку x-routed-by. Отмечу что сама маршрутизация по заголовку уже работает через VirtualService, EnvoyFilter - envoy  c lua  добавлен для демонстрации, так как в задании он требуется
- скрипты проверки check-istio.sh, check-canary.sh, check-fallback.sh, check-feature-flag.sh отработали, логи и скрины приложены
